# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A Windows WPF desktop app (.NET 8, `net8.0-windows10.0.19041.0`) that connects to Microsoft Flight Simulator via SimConnect, records a user-configurable set of simvars (plus joystick input) during landing, plots them via per-line formulas, and captures a screen recording of the sim window synced to that data. There is no `.sln` file — four sibling `.csproj` files are related by `ProjectReference`/folder nesting rather than a solution:

- **`LandingRecorder.csproj`** (repo-root-level within this folder) — the WPF app itself.
- **`WindowVideoCapture/WindowVideoCapture.csproj`** — a class library holding window-capture/video-encoding + the shared logger, with no SimConnect dependency. `LandingRecorder.csproj` references it. It gets the `Windows.Graphics.Capture`/`Windows.Graphics.DirectX` types from the Windows SDK projection that the .NET SDK supplies for the versioned `net8.0-windows10.0.19041.0` TFM (`Microsoft.Windows.SDK.NET.Ref` targeting pack + `WinRT.Runtime`). Don't go back to the old `Microsoft.Windows.SDK.NET`/`Microsoft.Windows.CsWinRT` preview NuGet packages: the former is under Microsoft's pre-release EULA, which forbids redistribution and production use. All three Windows projects must share that TFM, because a plain `net8.0-windows` project can't reference a `…10.0.19041.0` one. 19041 (Windows 10 2004) is also the minimum OS for the process-loopback audio capture.
- **`VideoCaptureManualTest/VideoCaptureManualTest.csproj`** — a manual console test harness for the capture/encoding pipeline (see "Manual video-capture test" below). References only `WindowVideoCapture`, not the main app.
- **`LandingRecorder.Tests/LandingRecorder.Tests.csproj`** — xUnit tests (`net8.0`) for the pure logic: the formula engine and the settings/recording models. It does *not* reference the main app (WPF + MSFS SDK); it compiles the dependency-free source files (`Formulas/Formula.cs`, `Models/*.cs`) directly via linked `<Compile Include>` items, so keep those files free of WPF/SimConnect/`AppLogger` dependencies.

## Commands

```
dotnet build
dotnet run
```

Run from `LandingRecorder/` for the main app. Building the main app requires Windows (`net8.0-windows10.0.19041.0` + WPF) and the MSFS 2024 SDK installed locally; `WindowVideoCapture`, `VideoCaptureManualTest` and `LandingRecorder.Tests` do not need the MSFS SDK (deliberately — see below).

```
dotnet test LandingRecorder.Tests
```

Runs the unit tests (formula parsing/evaluation, settings defaults/serialization, recording file round-trip). `LandingRecorder.csproj` excludes the nested test/harness folders from its own compile glob.

```
dotnet build -c Release
dotnet publish -c Release -r win-x64 --self-contained false -o publish
```

Release build output is `bin/Release/net8.0-windows10.0.19041.0/` (recordings, `settings.json` and `app.log` live next to the exe, so that folder also holds real captures). `publish` produces a copyable folder that includes the native `SimConnect.dll`.

`README.md` is the user-facing GitHub README (build prerequisites + a user manual covering every UI feature), with screenshots in `docs/screenshots/` taken from the Release build with a recording loaded. When adding or changing a user-visible feature, update the README's user manual too.

## Manual video-capture test

Besides the unit tests, `VideoCaptureManualTest/` is a real, permanent manual harness for the capture/encoding pipeline — run it after touching `WindowVideoCapture.cs`, the D3D11/WGC capture path, the Media Foundation encoding path, or `ProcessLoopbackAudioCapture.cs`:

```
dotnet run --project VideoCaptureManualTest
```

It opens a plain WinForms `Form` in its own process (rather than launching an external app like Paint) so the same process id can double as both the video capture target and the WASAPI process-loopback audio target, and records it in two ~6s Start/Stop cycles on the *same* `WindowVideoRecorder` instance (as the app does across consecutive landings) while continuously moving/resizing the window (to stress-test frame throughput and the ring-buffer slot recycling under load) with a looped system sound (`C:\Windows\Media\Alarm01.wav`) playing from that same process the whole time. For each output it checks the duration matches the wall-clock recording time (stale per-recording timestamps inflate it), decodes the audio track back to PCM and checks it isn't silence, scans `app.log` for errors, prints an overall RESULT line, and prints the output paths for manual playback verification. It builds independently of the main app/MSFS SDK because it references only `WindowVideoCapture` (now with `UseWindowsForms` for the `Form`/`SoundPlayer` it uses).

## Dependency: MSFS 2024 SDK path

The project references the SimConnect managed assembly via an `MSFS2024SDKPath` MSBuild property, defined in the csproj and defaulting to:

```
C:\MSFS2024SDK\SimConnect SDK\lib\managed
```

Override it if the SDK is installed elsewhere, either with an `MSFS2024SDKPath` environment variable or `dotnet build -p:MSFS2024SDKPath="D:\Some\Other\Path"`. If `Microsoft.FlightSimulator.SimConnect.dll` isn't found at the resolved path, the `EnsureSimConnectSdkPresent` target fails the build early with an explicit message rather than a generic reference-resolution error.

## Architecture

The app follows a hand-rolled MVVM layer (no CommunityToolkit.Mvvm or other MVVM package — `Mvvm/ObservableObject.cs` and `Mvvm/RelayCommand.cs` are the entire plumbing). `MainWindow.xaml.cs` is deliberately thin: it wires the ViewModel, hand-draws the plot-line graph onto a `Canvas`, and drives `MediaElement` playback — the handful of things that don't bind/command well in native WPF. Every other interaction (SimConnect, joystick input, video capture, the recording state machine, Save/Load) lives in `ViewModels/MainViewModel.cs` and the `Services/` classes it owns; the View never references `Services` directly.

- **[App.xaml.cs](App.xaml.cs)** — calls `RoInitialize`/`RoUninitialize` (combase.dll) and `MediaFactory.Startup`/`Shutdown` (SharpDX.MediaFoundation) once, paired at app startup/exit. `RoInitialize` is required because `WindowVideoRecorder` uses WinRT (`Windows.Graphics.Capture`) APIs directly via COM interop, not the managed WinRT projection; `MediaFactory.Startup`/`Shutdown` is the equivalent process-wide init for Media Foundation, kept at app scope rather than per-recording since the same `WindowVideoRecorder` instance is Start/Stop-cycled many times across a session.
- **[WindowVideoCapture/WindowVideoRecorder.cs](WindowVideoCapture/WindowVideoRecorder.cs)** (separate project — see "Project overview") — captures a specific window using `Windows.Graphics.Capture`/Direct3D11, and encodes frames to H.264/MP4 via a native Media Foundation `SinkWriter` (`SharpDX.MediaFoundation`), not OpenCV. Each captured WGC frame is GPU-copied (`CopyResource`, no CPU readback) into one of a small ring of dedicated `Default`-usage textures owned by this class — deliberately decoupled from WGC's own small frame pool, since handing WGC's own frame texture directly to the async hardware encoder risks it being recycled before the encoder finishes reading it. A ring slot is released back to the pool only after `SinkWriter.WriteSample` returns for it. Two non-obvious requirements discovered empirically (not documented by Microsoft/SharpDX): the D3D11 device must have `ID3D11Multithread::SetMultithreadProtected(true)` set before use, or `WriteSample` on a DXGI-backed sample hangs indefinitely; and a `MediaBuffer` created via `MediaFactory.CreateDXGISurfaceBuffer` has `CurrentLength = 0` by default and must have it set explicitly to `MaxLength`, or `WriteSample` throws `E_INVALIDARG`. Frames flow from the WGC `FrameArrived` callback through a bounded `Channel` to a dedicated async encoder task, so capture and encoding run on separate paths. The same instance is Start/Stop-cycled across recordings, so `Start()` resets all per-recording timing state (`ResetPerRecordingState`: first-frame zero-point, counters) *before* creating anything — the audio capture delivers chunks before `Start()` returns and the audio encoder reads `_hasFirstFrame`/`_firstFrameTimestampTicks`, so stale values from the previous recording would mis-stamp the next recording's first audio chunks. `Start()` runs all resource creation in `StartCore` inside a try/catch that calls `Stop()` on any failure, so a failed attempt leaks no GPU resources and never leaves the instance flagged as recording.
- **[Formulas/Formula.cs](Formulas/Formula.cs)** — hand-written expression engine for plot-line formulas over variables `x1..xN` (C# has no built-in that covers the needed functions; `DataTable.Compute` lacks them). Shunting-yard compilation to an RPN instruction array (modeled on `TextFunc` in SDBot's `plotter.js`), then evaluation on a preallocated stack — no allocation per `Evaluate`, since it runs per point per line on every 16ms redraw. Supports `+ - * / ^` (right-associative power, binding tighter than unary minus, so `-x^2` = `-(x^2)`), unary `-`/`+`, parentheses, `sqrt abs sin cos tan log log10 log2` (`log` is natural; functions require parentheses), constants `pi`/`e`. Numbers always use `.` as the decimal separator regardless of culture. Domain errors produce NaN/±Infinity rather than throwing; callers treat non-finite results as "no value". Not thread-safe (shared stack buffer) — fine since it's UI-thread only.
- **[Models/PlotLineSettings.cs](Models/PlotLineSettings.cs)** — `PlotLineSettings` (descriptive `Name`, `ShortName` used in the legend and cursor label, hex `Color`, ordered `Variables` = `x1..xN`, `Formula`, default `Min`/`Max`, `ScaleMode`, display `Unit`/`Decimals`), `PlotVariable`, and the enums `ScrollScaleMode` (`Both`/`MinOnly`/`MaxOnly`), `VariableSource` and `JoystickAxis` (all serialized by name). A `PlotVariable` has an explicit `Source`: `SimVar` (simvar `Name` + SimConnect `Units`) or `JoystickAxis` (`Axis`: X/Y/Z, X/Y/Z rotation, Slider1/2 — the standard DirectInput axes). Only the active source's fields are set/serialized (`WhenWritingNull`). `RecordKey` is the key in recorded points: the simvar name, or `JoyX`/`JoyY`/`JoyZ`/`JoyRx`/`JoyRy`/`JoyRz`/`JoySlider1`/`JoySlider2` for axes (`JoyY` deliberately matches recordings made when only the Y axis existed). Joystick axes are always *recorded* as percent of full deflection (-100..100, header units `percent` = `PlotVariable.JoystickUnits`); each joystick variable's `Scale` (`AxisScale.Percent`, or `Degrees` with its own `MaxDeflectionDeg`) is display-only, applied as `DisplayFactor` (maxDeflection/100) before the formula — so changing an axis's max deflection re-displays old recordings correctly. There is no global max-deflection setting.
- **[Models/DataPoint.cs](Models/DataPoint.cs)** / **[Models/Recording.cs](Models/Recording.cs)** — recording file format: `{"Variables": {name: units}, "Points": [{"TimeSeconds", "Values": {name: rawValue}, "TouchdownSim"?}]}`. `Values` holds *raw* values keyed by `PlotVariable.RecordKey` (simvar name, or e.g. `JoyY` for a joystick axis); formulas are applied only at display time, never on recording. A variable with no value at a moment is just absent from that point. The `Variables` header records the units each variable was recorded in, so a loaded file can be matched against current settings. `TouchdownSim` is always recorded regardless of settings; it's an edge-triggered flag omitted via `WhenWritingDefault` except on the point where it's `true`. `Recording.Load` re-keys dictionaries case-insensitively. Old flat-array files (pre-configurable-plot-lines) don't load; there's no compatibility shim (the files in `bin/Debug` were migrated once, with originals in `old-format-backup/`).
- **[Mvvm/ObservableObject.cs](Mvvm/ObservableObject.cs)** / **[Mvvm/RelayCommand.cs](Mvvm/RelayCommand.cs)** — the entire hand-rolled MVVM plumbing: `INotifyPropertyChanged` base with a `SetProperty` helper, and a parameterless `ICommand`.
- **[Converters/BoolToBrushConverter.cs](Converters/BoolToBrushConverter.cs)** / **[Converters/HexToBrushConverter.cs](Converters/HexToBrushConverter.cs)** — map `IsSimConnected` to the status-dot brush and plot-line hex colors to swatch brushes directly in XAML, keeping `System.Windows.Media` out of the ViewModels.
- **[Services/SimConnectService.cs](Services/SimConnectService.cs)** — owns the `SimConnect` connection and the connect/retry policy (retries every 5s on failure); callers call `Pump()` once per tick. Two kinds of requests, both every visual frame: (1) a fixed control definition (`PLANE ALT ABOVE GROUND` in feet, `SIM ON GROUND`) that is *always* monitored for auto-capture/touchdown logic and exposed as `HeightAboveGroundFeet`/`SimOnGround` — it's not recorded unless a plot line also references those simvars; (2) the configurable recorded simvars from `SetRecordedVariables` (the unique set across all plot lines, from `AppSettings.GetRecordedSimVars()`), each registered as its *own* single-`FLOAT64` data definition with fresh, monotonically increasing IDs. One definition per variable means an unrecognized simvar name loses only that variable: SimConnect reports it via `OnRecvException`, which is logged with the offending name by mapping `dwSendID` through `GetLastSentPacketID()` (returns the ID; no `out` overload in this SDK) recorded after each send. `SetRecordedVariables` while connected stops (`SIMCONNECT_PERIOD.NEVER`) and clears the old definitions before registering new ones. `GetRecordedValuesSnapshot()` returns a fresh case-insensitive dictionary of the latest values received since (re)registration.
- **[Services/JoystickInputService.cs](Services/JoystickInputService.cs)** — wraps DirectInput device enumeration/selection and axis reading: `ReadAxes(axes, values)` polls once per tick and writes each requested axis (only those used by plot lines, from `AppSettings.GetRecordedJoystickAxes()`) under its `RecordKey`, with raw 0..65535 mapped to -100..+100 percent for every axis, keeping DirectInput's direction (no inversion at recording time; the default JoyY line uses formula `-x1` so pushing forward reads positive); `GetAvailableAxes(deviceName)` lists the axes a device actually has (via `GetObjects(AbsoluteAxis)`, opening a non-selected device only briefly) for the Settings axis picker. There is no keyboard fallback: devices are selected by product name (`SelectDevice(string?)`/`RefreshDevices(deviceName)`), and a null name ("None" in Settings) — or a saved name that isn't currently attached — leaves no device selected, so `ReadAxes` writes nothing and no joystick values are recorded. `MainViewModel.StartRecording()` re-enumerates and re-selects the configured device (`EnsureJoystickForRecording`) so presence is checked at the start of every recording — a re-plugged device is picked back up, a missing one means no joystick values (and no joystick header entries) for that whole recording, so lines using it aren't drawn. The Settings dialog lists "None" first and keeps a saved-but-unplugged device as a "(not connected)" entry so confirming the dialog doesn't silently reset it. Has zero WPF dependency.
- **[Services/VideoCaptureService.cs](Services/VideoCaptureService.cs)** — locates the MSFS window (an exact, case-insensitive process-name match on `SimProcessName` wins over a main-window-title substring match; its own process is excluded) and drops the cached recorder — so the next `EnsureInitialized()` looks the window up again — when `SimProcessName` changes, when a `Start` fails, or when the cached window no longer exists (`IsWindow`; e.g. MSFS restarted). It never drops a recorder that is currently recording, since `EnsureInitialized` also runs on SimConnect reconnect and owns the `WindowVideoRecorder` instance lifecycle (start/stop, timestamped output path naming via `CreateOutputPath`). `MainViewModel` picks the data JSON path at recording start — next to the `.mp4` when video capture started, otherwise a standalone `flight-<timestamp>.json` (video disabled in settings, or capture failed to start) — and auto-saves it in `StopRecording()` (skipped if no points were recorded).
- **[Models/AppSettings.cs](Models/AppSettings.cs)** / **[Services/SettingsService.cs](Services/SettingsService.cs)** — user settings (joystick device, video recording enabled + MSFS process name, auto-capture start height AGL + stop delay after touchdown, and the plot lines) persisted to `settings.json` next to the executable. The record's property initializers *are* the defaults, used when the file is missing/unparseable and for any key absent from it; `DefaultPlotLines` reproduces the original six series (JoyY, pitch, elevator, height, VS, G) — pitch/elevator use formula `-x1` because SimConnect reports them positive-nose-down.
- **[ViewModels/SettingsViewModel.cs](ViewModels/SettingsViewModel.cs)** / **[SettingsWindow.xaml](SettingsWindow.xaml)** — modal settings dialog over an editable working copy; numeric fields are bound as strings and validated (OK disabled while invalid). The live app is only touched when the View, on OK, passes `ToSettings()` to `MainViewModel.ApplyAndSaveSettings` (applies, then saves); Cancel just drops the editor. Plot lines are edited via `PlotLineEditorViewModel`/`VariableEditorViewModel` (list with add/remove/reorder; per-line variable rows labeled `x1..xN` by position, each with a Source picker switching between simvar name/units and a joystick-axis picker). The axis pickers share one fixed list of `JoystickAxisOption`s owned by `SettingsViewModel`; changing the dialog's joystick only toggles each option's `IsAvailable` (unavailable axes stay listed but disabled, labeled "(not on device)"), never rebuilds the list — rebuilding would make the bound ComboBoxes drop and write back their selection. With None or an unattached device, all axes stay enabled. A line's color is a hex text box plus a swatch `ToggleButton` opening a `Popup` with the 24-color `PlotLineEditorViewModel.ColorPalette` (picked for readability on the dark graph background); the swatch click handler in `SettingsWindow.xaml.cs` just sets the selected line's `Color`. Validation compiles each formula against its variable count and rejects the same simvar used with different units in different lines (each simvar is requested and recorded once). The Settings button is bound to `CanOpenSettings` (`!IsRecording`), and `ApplyAndSaveSettings` also refuses while recording.
- **[ViewModels/MainViewModel.cs](ViewModels/MainViewModel.cs)** — composes the four services and owns everything else. Its `DispatcherTimer` runs for the app's entire lifetime (started once from `Initialize()`), independent of recording state, so `SimConnectService.Pump()` and the connection status are always live even if the user never starts a capture; the timer's interval itself switches between `DisconnectedTickInterval` (5s, matching `SimConnectService`'s own reconnect cadence) while not connected and `ConnectedTickInterval` (16ms) once connected, flipped in `SimConnectService_ConnectionStateChanged`. `IsRecording` is the single source of truth for "currently capturing" — the Start/Stop button (`ToggleRecordingCommand`) directly and immediately calls `StartRecording()`/`StopRecording()`, which start/stop video capture and point collection right away, with no height-threshold gating. The bindable `AutoCaptureEnabled` property (defaults to `false`, bound to the "Auto capture" checkbox) layers the original automatic behavior on top of that same state from within `Tick()`: height crossing above→at-or-below `AutoStartHeightFeet` calls `StartRecording()` if not already recording, `SimConnectService.SimOnGround` transitioning `false`→`true` marks ground contact, and `AutoStopDelayAfterTouchdownSeconds` after ground contact calls `StopRecording()` — all skipped entirely when the checkbox is unchecked, so a manual-only capture never auto-stops. Manual and automatic triggers share the same `StartRecording()`/`StopRecording()` calls, so the button remains fully functional (and can override an auto-started or auto-timed capture) regardless of the checkbox state. `Tick()` computes the `isTouchdownSim` flag every tick, unconditionally (not gated on `AutoCaptureEnabled`, unlike the auto-stop timer, since it's recorded data as well as capture-control input): it's true exactly on the tick where `SimOnGround` transitions `false`→`true`, guarded with a nullable `_previousSimOnGround` so the very first tick after connecting — where there's no real previous state — can never spuriously fire it (mirroring the `double.NaN`-sentinel guard already used for the 100ft auto-start check). The same flag both seeds `_groundContactTimeUtc` for the auto-stop timer and is passed straight into that tick's `DataPoint` when recording — a single source of truth rather than two independent touchdown checks (an earlier version used a second, CG-height-crossing-zero signal for this; it was removed as redundant). Each recorded `DataPoint` takes `SimConnectService.GetRecordedValuesSnapshot()` plus the used joystick axes (`JoystickInputService.ReadAxes`). Also owns the `DataPoint` list (capped at `MaxPoints`), Save/Load and auto-save of the recording JSON, and all bindable state/commands (`ToggleRecordingCommand`, `ResetCommand`, `PlayVideoCommand`, `PauseVideoCommand`). `PlotLines` (`ObservableCollection<PlotLineViewModel>`) is rebuilt from settings on every apply (keeping per-line visibility by name; ranges reset to the configured defaults). `_dataVariables` (name → units of the displayed data: the loaded file's header filtered to variables that actually have values, or the live recording's configured simvars + used joystick axes if a joystick is present; null after Reset) drives each line's availability — a line whose variable is missing or was recorded in different units isn't drawn and is dimmed in the legend with the reason as tooltip. It raises a single coarse `GraphInvalidated` event rather than granular per-field notifications, since the View's graph redraw always rebuilds everything from `Points`/`SelectedPointIndex`/`PlotLines` anyway.
- **[ViewModels/PlotLineViewModel.cs](ViewModels/PlotLineViewModel.cs)** — runtime state of one line: compiled `Formula`, current zoomable `Min`/`Max`, `IsVisible`, `IsAvailable`/`UnavailableReason`, and `Evaluate(DataPoint)` (null if any variable is missing at that point or the result isn't finite, so the polyline skips that point). `Zoom(wheelDelta)` scales the span by 10% per notch according to `ScaleMode` (wheel up zooms in). An invalid formula from a hand-edited settings.json makes the line unavailable rather than crashing.
- **[MainWindow.xaml.cs](MainWindow.xaml.cs)** — constructs the services + `MainViewModel` and sets `DataContext`; hand-draws the graph (`DrawGraph`/`AddLine`/`AddText`/`AddValueLabel`) whenever `GraphInvalidated` fires; owns all imperative `MediaElement` calls (`Play()`/`Pause()`/`Position`/`MediaOpened`/`MediaEnded`) since those don't have a data-binding equivalent in WPF (the volume `Slider` binds directly to `VideoPlayer.Volume` by `ElementName`, with `VolumeToTextDecorationsConverter` striking through the "Vol" label at zero); and owns the Save/Load file dialogs (calling into `MainViewModel.SavePoints`/`LoadPoints` for the actual JSON IO). Click-drag scrubbing on the graph canvas converts pixel coordinates to a time value in the View, then delegates the nearest-point lookup to the ViewModel. The matching video seeks are coalesced (`_pendingSeek`, applied at most every 50ms by `_seekTimer`, plus once on release) because a seek per `MouseMove` makes `MediaElement` stall on a frozen frame until Pause/Play; `ScrubbingEnabled` is permanently on in XAML (not toggled per drag), the player is muted for the duration of a drag (scrub seeks each play an audio snippet, which sounds like chopping) and its previous `IsMuted` restored afterwards, and `EndScrub` also runs from `LostMouseCapture` so playback resumes even without a MouseUp. This is unaffected by the plot lines' Y-axis ranges since it only ever computes the X (time) axis. Right-drag on the canvas draws a dashed selection on the topmost `MagnifierCanvas`; releasing shows a 2x live magnified inset (a `Rectangle` filled with a `VisualBrush` of `VideoPlayer`, `ViewboxUnits=Absolute` over the selection — the canvas and player are coincident so their coordinates match) that can be left-dragged and is removed by right-clicking it, a plain right-click without drag, or a change of `VideoSource`. A legend overlay (`LegendPanel`, initially positioned once near the graph's top-right corner in `LegendPanel_SizeChanged`, then draggable by its "Data & Scale" caption bar via its `Margin` and collapsible with the ▼/▶ glyph; on top of both the video and the canvas) is an `ItemsControl` over `PlotLines` (columns aligned via `SharedSizeGroup`) with one row per line — a color swatch, its `ShortName` (full `Name` as tooltip), its live range text, and a visibility `CheckBox` — and scrolling the mouse wheel specifically over a row's range `TextBlock` (which needs `Background="Transparent"` to be hit-testable at all) calls `MainViewModel.ZoomPlotLine` for that row's `DataContext`; there is no canvas-wide scroll-to-zoom. Each drawn line also gets a colored handle dot at its first point (`AddLineHandle`): scrolling over it zooms with the same step as the legend row but anchored at the dot's own value (`PlotLineViewModel.ZoomAround`, ignoring `ScaleMode`) so the dot stays under the mouse instead of running away — the legend's scroll still follows `ScaleMode` — right-clicking it resets the range to the configured default (`PlotLineViewModel.ResetRange`; the event is marked handled so the canvas doesn't start a magnifier selection), and left-dragging it pans the line's range (`MainViewModel.SetPlotLineRange`, computed from the range at drag start so it doesn't drift). Because `DrawGraph()` rebuilds every canvas child each tick, the dot can't hold the drag itself — drag state lives in `_lineDrag` and `GraphCanvas` (which persists) captures the mouse; the handle's `MouseLeftButtonDown` marks the event handled so it doesn't start scrubbing, and `LostMouseCapture` clears a stuck drag. Each line maps its own `[Min, Max]` onto the full plot height, values are clamped into range so an out-of-range spike doesn't draw off-canvas, and lines that are hidden or unavailable are skipped along with their cursor value label (`ShortName value unit`). A final legend row for "Touchdown" has a dashed-yellow-line swatch (a `Line` with `StrokeDashArray` instead of the other rows' solid `Rectangle`, to visually match what it represents) and a `TouchdownVisible` checkbox, but deliberately no range column/`MouseWheel` handler — unlike the plot-line rows, it's a marker of a moment in time, not a scalable value series. `DrawGraph()` draws one full-height dashed yellow vertical marker line (via the `AddDashedLine` helper, which sets `StrokeDashArray`, alongside the existing solid-line `AddLine`) per point where `DataPoint.TouchdownSim` is `true`, gated on `TouchdownVisible` and drawn before the plot-line polylines so the continuous data lines stay visually on top.
- **[WindowVideoCapture/AppLogger.cs](WindowVideoCapture/AppLogger.cs)** (separate project, `public` so the main app and the test harness can both call it) — minimal static file logger writing `app.log` next to whichever executable is actually running (main app or `VideoCaptureManualTest`). The log is kept across runs (each run starts with a `===== <process> started (pid N) =====` marker) and never throws. Before a write, if `app.log` exceeds `MaxLogBytes` (1 MB) it's rotated by `LogRotation.Rotate` (same file, separate class so tests can call it without triggering the logger's static initialization): archives are `app-1.log` (oldest) .. `app-5.log` (newest); existing archives are first compacted to 1..k keeping their order, and when all 5 exist `app-1` is deleted and the rest shift down, so the new archive is always the highest number. The test project links `AppLogger.cs` to test the rotation, so keep it free of Windows-only dependencies. `VideoCaptureManualTest`'s error scan only considers log lines timestamped after its own start.

## Known limitations (accepted, deliberately not fixed)

- **Window resize mid-recording:** the WGC frame pool is created once per `Start()` at the window's size then and is never recreated, so resizing MSFS or toggling fullscreen *during* a recording makes every later frame's `CopyResource` fail (frozen video for the rest of that recording). The next recording is fine since `Start()` re-reads the size.
- **Go-around without touchdown:** auto-stop only arms on the `SimOnGround` false→true transition, so after an auto-started approach that goes around, recording continues until the next touchdown (one long recording; data capped at `MaxPoints`). Likewise a flight reset from the air onto the runway can auto-start a recording with no touchdown to stop it.
